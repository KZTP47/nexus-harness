# Email assistant

Open **Email assistant** in Nexus Harness. Choose your Claude or Codex connection and model, then choose a mail connection method:

- **EmailEngine mailbox service:** the selected mailbox infrastructure. On Windows, choose **Set up local mailbox service** to download pinned, checksum-verified EmailEngine and Redis runtimes on first use. Nexus starts private loopback services and protects their generated passwords/API token with Windows DPAPI. Then choose **Add mailbox / sign in**, complete the provider's setup, **Find service mailboxes**, select the intended account, and connect. Outlook/Gmail API sign-in still requires a publisher application registration; installing the service cannot infer one from a browser login. Under Advanced, you can instead supply an existing EmailEngine service address and API token. Nexus keeps its own AI editor, mail memory and Kestra workflows.
- **Browser sign-in:** open Outlook or Gmail in a separate Nexus-owned Edge/Chrome window, sign in, then finish connecting in Nexus. No client ID is required. The saved browser profile is reused after restart; Nexus does not take cookies from your ordinary browser. Browser reading can mark messages read. This DOM reader walks the scrollable inbox in bounded batches, preserving its position and unfinished rows in a mailbox-bound cursor across checks and restarts. Each pass collects up to 200 conversations and reads up to ten; these are batch sizes, not a permanent history cutoff. Conversations with more than 20 visible messages continue in later batches. Both supported Outlook Focused/Other tabs retain independent traversal progress. Collapsed messages, separate pagination controls, and mail outside Inbox are not exhaustively imported; unsupported layouts and expired sessions produce errors.
- **Classic Outlook:** discover the mail accounts in the installed Windows classic Outlook profile and choose one. No client ID is required. New Outlook does not expose this interface; use browser sign-in for it. This adapter reads Inbox without marking messages read.
- **Registered API sign-in:** retains Microsoft Graph/Gmail OAuth for publishers or organizations that supply their own legitimate application registration. Advanced registration fields apply only to this method.

Browser connections prepare drafts in Nexus and can submit the exact reviewed reply through the mailbox website after **Review & send reply**, then **Send**. No application registration is required for this path. The adapter verifies the signed-in mailbox, original message, recipient and editor contents before using the website's Reply and Send controls. Unsupported or ambiguous layouts stop the operation. Classic Outlook connections still export approved `.eml` replies for you to send.

Choose **Visible browser** (headed) or **Background browser (headless)** on the Outlook/Gmail card. **Save browser mode** updates an existing connection without replacing its mailbox or memory. Sign-in always opens visibly; subsequent checks and approved sends use the saved mode. An expired session requires visible sign-in again. Headless means the browser has no visible window; it does not make Nexus an always-on cloud service.

Browser sending currently recognizes supported English Reply/Send controls and send acknowledgements. Different languages or website layouts may stop the operation; an unrecognized acknowledgement after Send produces an unknown outcome. Original messages must still be uniquely visible and unchanged. An open browser reply editor blocks polling and mode changes until you finish or close it, so Nexus does not discard that work.

Automatic checks run while Nexus is open and resume when the selected project is reopened. The default local check interval is 60 seconds. Whole-second intervals from 1 to 86400 seconds are supported. Choose **Save assistant settings** to apply the interval or stop automatic checks; the UI distinguishes unsaved input from the saved value. Scheduling checks run twice per second and target the saved interval between scan starts. A running scan is never overlapped: if it takes longer, the next due scan starts after it finishes. Mail delivery, browser rendering and AI drafting are additional latency, so a three-second interval is not a promise of a ready reply within three seconds. Imported messages and draft state are durable and deduplicated.

The inbox list reports when more messages remain and shows newest messages first, the latest check, saved interval, actual scan duration and next due check beside **Check inbox now**. Messages without subjects are supported. Browser checks retain the dedicated inbox page and skip successfully read unchanged rows using a versioned, account-bound cache of hashes. At most one unchanged row per tab becomes eligible for rotating reconciliation after 30 seconds; this is not a full-mailbox discovery deadline. This fallback finds changes that do not alter the visible row summary. Failed and new/changed rows take priority and remain eligible if the read budget is exhausted. Browser and classic Outlook imports have no reliable arrival timestamp, so the first scan after connecting, reconnecting with a changed connection, or turning automatic checking back on is treated as history: the mail it finds is kept as context but is not drafted or announced. That baseline ends when the mailbox reports no remaining backlog (at most 200 passes); mail discovered by later scans is new and is drafted. During the baseline, a message the mailbox dates after the baseline began is already new; undated mail found during it stays history. Mail found while automatic checking was off (for example by **Check inbox now**) also stays history when checking is turned on. A first IMAP check reads only the newest 50 messages and continues in batches of 50 while more remain; a changed UIDVALIDITY re-reads the folder as history (resuming after an interrupted check) and known mail is recognised by its Message-ID. IMAP eligibility uses the server's arrival time (INTERNALDATE), so delayed or greylisted mail written before checks began is still new. Corner notifications cover only mail imported by the scan that drafts it, never older stored mail. HTML-only mail is read as text, never rendered: Nexus follows the browser's reading of the markup (implied end tags, inline styles such as `display:none`, `visibility:hidden`, `opacity:0`, zero font size and zero clipped boxes, closed `<details>` and `<dialog>`, iframes and other never-shown elements). Text the sender hid from view is never shown as the email and is not the body the assistant drafts from; it is given to the AI only as a separately labelled, untrusted block (at most 4,000 characters), shown for awareness and never to be followed. Only literal, unambiguous signals hide text: a `calc()`, `min()`, `clamp()` or `var()` value, or an invalid size, never hides anything, and zero-height table cells or padded boxes are treated as visible, because dropping words the sender meant you to read is the worse failure. Reading is linear and bounded: at most 2 MB of HTML and about two seconds per message; beyond that a plain reader keeps every word (logged). IMAP decides which mail is new from UIDs and the server's own arrival times rather than this computer's clock; mail without a Message-ID is recognised by its sender, subject, text and Date. The reader is best effort. Known residual: hiding through a `<style>` class rule (for example `.pre{display:none}`) is not evaluated, so such text is read as visible; the draft is still reviewed before anything is sent. Mail with no visible text (only images, or only hidden text) is imported as having no readable text rather than drafted from hidden text. A message Nexus could not import stays in your mailbox and is listed under import issues until a later check imports it or you dismiss the note; IMAP and API checks do not read it again on their own.

The EmailEngine connection also uses periodic checks while Nexus is running. Each check advances a paginated Inbox pass and checks the newest page; it uses mailbox-service pagination rather than the browser reader's rendered inbox. This is polling reconciliation, not a subscribed durable arrival-event stream. Messages removed from Inbox before a check may be missed. Initial history is retained without automatically drafting every old message. Automatic-draft eligibility uses message timestamps relative to the connection baseline: missing or invalid timestamps become history, and delayed or backdated mail may need a manual draft. Sleep, shutdown, expired authorization, server outages and throttling delay processing. An always-on EmailEngine server alone does not run Nexus's desktop AI workflows while the computer is off.

Oversized or unavailable messages are reported rather than drafted from silently truncated content. Historical completeness, large-mailbox throughput and long unattended reliability still require live validation; do not interpret a connected indicator as proof of those properties.

After a draft arrives, edit it directly or enter a request such as “Make this shorter” and press **Revise with AI**. The AI works from your current edited text using the currently selected assistant and model, including after you change assistants. A newer edit cannot be replaced by an older AI response. Preferences are learned from explicitly approved edits when **Learn from my edits** is enabled.

For a first try, select **Imported mail**, expand **Import an email**, and paste a message or choose an `.eml` file. Select the message and press **Create draft**. The bundled Kestra engine starts when needed and pauses the workflow for your review. Compare the original with your reply, save edits, and approve when ready. Imported mail produces an `.eml` file through the desktop Save dialog that you can open in your mail application; it does not send automatically.

The registered API connections for Outlook/Microsoft 365 and Gmail/Google Workspace use their provider APIs with refreshable OAuth access. Incoming message bodies are converted to readable text; cloud attachment content is not downloaded or used for drafting. **Save assistant settings** changes the AI route and automatic checking; **Disconnect mailbox** stops checks and removes locally stored access tokens while preserving drafts and preferences. Reconnect uses the same mailbox identity.

The application publisher must first supply real desktop OAuth registrations. This development build does not contain registered client IDs, so it honestly shows registration required. See [publisher setup](email-oauth-setup.md); normal users should not need to fill in these advanced fields once a registered release is supplied. API sign-in remains unverified until those registrations and a test mailbox are available; browser sign-in is a separate connection path.

For other services, expand **Manual mailbox setup or imported mail**. An IMAP mailbox can check for new messages automatically and draft them while Nexus is open. Configure incoming IMAP over TLS and outgoing SMTP over TLS with the mailbox's password or app password. Only **Review & send reply**, then **Send** authorizes delivery. Import/export remains available when organizational policy prevents connecting an account.

**Learn from my edits** extracts reusable preferences from approved changes. Uncheck it for a one-off reply. Received correspondence remains attributable context; the indexed archive can retrieve older relevant messages beyond the immediate sender's recent mail. Retrieval uses bounded lexical search and query expansion, not guaranteed understanding of every paraphrase or an unlimited archive in each prompt. Learned preferences are separate from received mail; inspect, edit or delete them under **What your assistant has learned**. Mailboxes do not share correspondence or preferences. This is persistent retrieval and preference learning, not model-weight training. An approved exported or queued reply may supply style feedback, but it must not be represented as confirmed sent correspondence.

Original drafts and saved edits survive restarts. Failed generation and failed learning can be retried without authorizing another send. A workflow interrupted before submission may resume; an interruption during submission requires outcome reconciliation rather than an automatic resend.

## Sending and outcome labels

**Review & send reply**, then **Send** authorizes the exact reviewed reply. EmailEngine uses the source message's reply reference so the server constructs a reply in the intended conversation. Nexus records a submission intent before contacting the server and attaches a stable idempotency key; EmailEngine 2.52.0 or newer is required for that contract.

Approvals made by older browser versions authorized export only. Those drafts require a fresh explicit send approval in the updated UI; upgrading cannot turn an export approval into permission to send.

- **Queued / submitted to EmailEngine:** the service accepted the job. This is not yet evidence that the mailbox provider accepted the message.
- **Sent / provider accepted:** provider or SMTP submission has been reported as accepted. This is not proof of recipient delivery or reading.
- **Browser confirmed:** the mailbox website displayed a new send acknowledgement and closed the reply editor. This is not proof of recipient delivery. A missing acknowledgement after Send leaves the outcome unknown.
- **Exported:** an `.eml` file was produced. Nexus has no evidence that it was sent elsewhere.
- **Unknown outcome:** submission may have succeeded, but Nexus cannot establish the result. Check delivery status, the server outbox and Sent Items. Nexus does not automatically resubmit the reply.

Server idempotency has finite retention; the key is not a permanent exactly-once guarantee. A missing outbox entry is also not evidence of success: completed jobs may be removed, but a missing job can have other causes. Unknown outcomes stay unknown until evidence resolves them. EmailEngine may retry a job already in its own queue according to its server policy; that differs from Nexus creating a replacement submission. No automatic duplicate submission is authorized by a retry of AI generation or preference learning.

Mail, drafts, exports and preferences live in the selected project's private `.harness/email-studio` directory. Windows DPAPI protects stored mailbox passwords and OAuth tokens for the current Windows user. The selected AI provider receives the bounded message context needed to draft or reflect. The email feature never uses the Nexus project-development Obsidian vault.

Kestra and Java are bundled with the Windows installer and run without Docker or a separate Java installation. Local Nexus/Kestra listeners are restricted to loopback and the API requires authentication. The pinned runtime is Kestra 1.3.38 with a private Java runtime; its H2 database is a local desktop orchestration store. Upstream recommends PostgreSQL/MySQL for production server deployments. Nexus's mail database remains the authority for approval and recorded delivery state, separate from Kestra state. EmailEngine and Redis are downloaded on demand or supplied by an external service; their payloads are not embedded in the installer. Initial local setup needs roughly 160 MB of downloads plus extracted runtime/data space.

## Verified behavior and remaining release work

### Activity feedback and Outlook reply diagnosis

Generation, AI revision and approved delivery show activity beside their controls, with elapsed time when a start timestamp is available. Actual generation/finalization callbacks are tracked separately from merely submitting a Kestra workflow. A running indicator reports an active operation, not proof that the AI provider is healthy; stale snapshots stop the animation. Failures and uncertain delivery appear beside approval/retry controls.

**Original AI draft** is the read-only first suggestion. **Your reply** starts as its editable copy, so a user can approve it unchanged, edit it directly, or request an AI revision. Prefilling does not mean a revision was requested.

A reported Outlook send failure reached the finalize callback but stopped before dispatch. Live DOM inspection reproduced two compatibility problems: zero-height empty message placeholders were selected as message bodies, and Outlook's editable To field used recipient chips that the adapter did not recognize. The recipient check was reproduced without sending correspondence. Later retries encountered the composer left open after the preflight failure. Existing composers are protected from overwriting; finish or close an existing mailbox composer before retrying an approved workflow. The original first-attempt error was not retained after subsequent attempts, so the live reproduction explains the observed failure but cannot reconstruct every historical attempt.

The authorized live retry also exposed a separate recovery defect: a replacement Kestra workflow attempted generation again and rejected a changed AI route before delivery. Recovering an approved reply must preserve its exact text and approval revision, without calling the AI again. Mailbox identity, source-message and send-approval checks still apply. If the AI connection changed, learning reports a separate error; an explicit learning retry authorizes use of the current connection without resending the reply.

Further native Outlook checks cover delayed message rendering, a saved draft appearing after the received original in the same conversation, and editable proofing paragraphs. Sending selects the referenced original and waits for its exact identity/content; default inbox extraction excludes recognized unsent envelopes. Composer entry waits for a bounded stable layout, uses native keystrokes, and compares logical proofing lines without collapsing arbitrary whitespace. A late provider change still fails closed before dispatch. A running retry is shown as active even while its earlier error remains stored.

Regression fixtures represent these structures using synthetic identities. No mailbox address, message content, private profile path or machine-specific identifier belongs in product code or fixtures. A separately authorized live Outlook reply reached the original sender; the user confirmed arrival including the requested number lines. Sent Items contained the approved text with Outlook's native empty-paragraph representation. This is one verified Outlook delivery, not Gmail or unattended production certification.

Outlook's send acknowledgement was not recognized during that test, so Nexus conservatively recorded an unknown outcome and prevented another dispatch. For a browser reply with an unknown outcome, a user who checked Sent Items or confirmed recipient arrival can explicitly record a verified send. This updates local delivery evidence only; it never invokes Send. Provider UI acknowledgement coverage remains a known limitation. Learning after an AI connection change remains a separate explicit retry.

Earlier live browser testing demonstrated an arriving Outlook message triggering an AI draft and an AI revision in Nexus. Synthetic tests exercised persistent preferences with a real AI route. Browser-send regression tests use synthetic provider DOM fixtures; the feedback amendment above adds one recipient-confirmed Outlook delivery. A live Gmail delivery remains an acceptance boundary.

The new EmailEngine adapter and workflow behavior have automated contract tests. Initial native experiments exposed a real incompatibility: Garnet answered health and listing requests but then failed queue workers on unsupported `XREAD`; it is not a supported substitute. Docker Desktop also could not start on the test host.

A subsequent portable Redis 8.10.1 community Windows build with native EmailEngine 2.80.1 passed a stronger isolated test: duplicate idempotency keys returned the same queue job, queued mail survived restarting both processes, and an immediate job delivered exactly one expected message to a synthetic SMTP server on loopback. No real recipient was contacted. This proves that a native pair can run without a global service installation, not that its packaged provisioning or unattended production use is certified. Redis's community Windows build and its Cygwin dependencies require pinned, verified artifacts. EmailEngine reported inactive entitlement/limited mode while allowing this single-account test; that result must not be extrapolated to unrestricted production capability. Legal decisions remain with the legal department.

Another discovered limitation is startup readiness: `/health` became successful before a restarted account worker could accept submissions. A submission during that interval returned HTTP 503; waiting for the worker resolved it. Queue/server health, account readiness and sending capability must remain separate checks.

The actual managed setup module was also tested in a fresh temporary project with real DPAPI, using preseeded pinned artifacts that its normal download path reverified before extraction. Redis accepted password-protected configuration through stdin, the generated API token authenticated, and restart preserved the service address, secrets, token and a synthetic account. This proves the managed lifecycle against real binaries. It does not substitute for the packaged UI/clean-machine test or imply publisher sign-in is configured.

Subsequent parent verification exercised an actual first download through Electron in an empty temporary project. Both packaged flows passed: saved draft/preferences/export after restart, and private mailbox service restart plus hosted sign-in. A missing serviceUrl initially caused HTTP 500 when adding a mailbox; setup now configures its actual local address, and sign-in form creation passes before and after restart. The current tests cover 185 passing email cases, 20 UI/browser cases, a separately enabled real Kestra restart/resume workflow, real AI drafting/revision/learning with synthetic mail, and native queue/restart/idempotency/loopback SMTP experiments. Another regression caught replacement of a remote mailbox behind an unchanged service ID; synchronization and submission now revalidate its connected identity. The final deployment passed74 tests against its bundled Python and matched17 email source files exactly. These are development acceptance checks on one Windows host, not an unattended production certification.

An actual mailbox connection through this new service, a received threaded reply, token refresh/revocation, sleep/wake recovery and a measured long-running soak remain acceptance work. Do not advertise all six user requirements as fully verified. See [architecture decision](email-architecture-options.md) for the selected path and deployment limitations.

## Automatic recipient learning

The learning area has two tabs. **What your assistant has learned** preserves the existing manual preferences. **What your assistant has learned AUTOMATICALLY** shows reusable preferences extracted after a successful **Revise with AI** request, grouped by the exact reply recipient. You can edit or delete each automatic preference; editing it keeps its recipient scope.

Learning happens without approving or sending the reply. The AI extracts at most three short style or explicitly recurring wording preferences, with evidence from the requested change. One-off facts, dates, promises and message content should not become standing preferences. The revision status reports whether learning succeeded, found no reusable preference, could not identify one recipient, or failed. A learning failure keeps the revised reply available. The existing **Learn from my edits** checkbox controls the separate approval-time learning step.

Automatic records live in the private SQLite preference ledger, with source draft/revision, category, recipient, mailbox fingerprint, schema and learning contract. Recipient identity uses the single Reply-To address when present, otherwise the sender; display names and casing normalize, while distinct addresses and plus aliases remain separate. Ambiguous recipients fail closed. Changing mailbox identity or an incompatible learning contract/schema prevents stale records from influencing replies. Same-category inferred rules are replaced by newer learning; explicit user edits retain priority.

Drafting and revision use only matching recipient learning. Earlier received messages and approved writing examples supplied to drafting are also restricted to that recipient. Legacy approved-edit preferences are matched to their source recipient; preferences explicitly added by the user remain mailbox-wide. This deliberately removes cross-recipient history from draft context to prevent family wording or customer context mixing.

The extraction decision still depends on the selected AI model; the recipient boundary is enforced by the engine. Tests cover recipient/mailbox isolation, Reply-To, restart, changed configuration/schema, stale or failed revisions, supersession and edit/delete persistence. A real AI test with synthetic mail learned a warm tone and Swedish language and declined to learn a one-off apple-pie statement. No real mail was sent for this feature's verification.

### Learning outcomes and retries

The automatic tab also shows each recipient's saved revision requests and learning outcomes, even if no preference was extracted. It distinguishes successful learning, no reusable preference, extraction failure, and earlier requests whose outcome was not recorded. New revisions retain a bounded history of the latest twelve requests and their outcomes.

**Retry learning** re-extracts the selected saved request without revising, approving or sending the reply. Earlier requests recorded before outcome history was introduced can be retried using only their explicit instruction; missing original/revised text is not invented. The current draft revision, request fingerprint, mailbox identity and provider connection are checked around the operation. Requests to fix spelling, grammar or punctuation are eligible writing preferences, unless explicitly limited to one reply. One-off factual content still should not become a standing preference.

Earlier revisions can exist without a recorded learning outcome. The automatic tab exposes this state and offers a guarded learning retry. A successful retry saves a recipient-scoped preference without changing reply text, draft revision, approval or delivery state.

Recipient template learning: explicit requests covering future mail from one recipient can learn both omitted template content and its replacement literal, including addresses and numeric footer lines. Recipient provenance accompanies draft/revision preferences so an explicit recipient correction can override a conflicting mailbox-wide default. One-reply facts remain ineligible. Existing unsuccessful requests can be recovered using Retry learning; saved replies are preserved.

Browser inbox import recognizes Outlook message envelopes without a labelled wrapper, including rendered empty-body and meeting-cancellation messages. Empty messages remain visible but do not generate automatic drafts. Parser upgrades retry previously failed rows without losing inbox traversal progress. The inbox shows the imported-message count separately from the navigation tab's explicitly labelled draft count; detailed import issues remain expandable.

Outlook embedded conversation cards are switched to their standard email view only when the rendered conversation heading identifies the selected inbox row. Controls inside email content are excluded. Large import backlogs drain before automatic draft preparation, so a slow draft service cannot strand older inbox batches.

Reviewed replies open a mail draft window with From, To, Subject, Message, Send, and Cancel. The conversation headers are read-only; the message can be edited before approval. Cancel sends nothing. Browser sending reopens a closed saved browser session, refreshes a stale connection, and locates the original conversation across the virtualized inbox before verifying the message and recipient. A genuinely expired login requires sign-in; moved, deleted, or ambiguous originals remain unsent. An uncertain send is never automatically retried.

Choose **Send original AI draft** or **Send your reply** above the two versions; the highlighted version is loaded into the mail window. The window also offers **Version to send**. A definite pre-send failure keeps **Review & send reply** available so you can review, change versions, and retry from the same button. Reply preparation uses the same verified message envelope as reading, and retries once after refreshing the mailbox if the original row or Reply control is temporarily unavailable. Uncertain delivery stays blocked from resending.

Both revision and sending start with a readiness check. Metadata-only draft revision changes are reconciled while preserving visible unsaved text. A definitely-unsent approval is returned to review before AI revision. Browser send readiness refreshes the mailbox and verifies the exact original message and its Reply control before the review window opens; it cannot open a composer or dispatch a message. Sending verifies those conditions again after explicit approval. Successful preparation clears terminal errors from previous attempts. Conflicting saved text and uncertain delivery are preserved rather than overwritten or resent.

Browser reply entry uses one native editing transaction with an escaped preformatted text block instead of typing every character, avoiding per-action timeouts on long paragraphs in Outlook’s proofing editor. The exact body and recipient are still checked before dispatch. If entry fails, a private hash-only record binds the interrupted composer to this draft, original message, mailbox, recipient, remaining text, and a marker on the live composer. A subsequent review/send can resume that unchanged composer, including Outlook’s separate reading/editing tabs. External edits, changed recipients, changed originals, and uncertain sends are never silently overwritten or retried. Browser failures identify the failed send stage rather than promising recovery on an unrelated inbox scan.

Outlook can regenerate rendered message IDs when switching reading/editing views. Reply recovery reconciles an ID only when the pane positively identifies the original conversation and exactly one complete sender/subject/body match exists. Changed content, ambiguous duplicates, and another conversation fail closed.

Send actionability is checked before persisting the no-resend barrier, so a disabled or blocked button remains retryable. After dispatch, Outlook confirmation can also use a separate read-only Sent Items view: it records existing message IDs and timestamps before sending, then requires a new message in the exact conversation with the approved body, recipient, and mailbox sender. This handles missing send toasts and Outlook reopening another saved draft. Existing sent messages, quoted copies, and uncertain evidence do not authorize a second Send. Verification tabs close on every outcome, and uncertain receipts retain the failed stage without storing message content.
