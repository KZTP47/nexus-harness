# Nexus Harness 0.2.17

Saved-work recovery could deadlock the server at startup: recovery held the
server authority lock while waiting for the scheduler lock, and the scheduler
called back into server authority while holding its own lock. Saved chats kept
loading and selected-agent connection diagnosis never returned, although a
route-only provider status probe still worked.

- Runtime startup, replacement and shutdown now share a separate lifecycle
  lock. Recovery and close run outside the server authority lock; callers share
  one fully recovered runtime. A failed recovery retains ownership of any
  draining agent step, and a closed runtime cannot start another queued step.
  A settings reload rejected by a racing worker safely reopens the unchanged
  configuration after that worker drains.
- Listing saved chats no longer replays every collaboration history. Selected
  collaboration diagnostics return a temporary busy state during a write,
  without treating contention as corruption or offering a destructive reset.
- Startup journal verification reads its integrity key once per transaction,
  checks every record, and rechecks the key at the end. Large saved histories
  no longer cause thousands of repeated key-file operations under board authority.
- Connection diagnosis retains its pending/error state across refresh, has a
  30-second deadline, supports retry, and rejects stale results after navigation
  or route changes. Diagnosis itself sends no model prompt.

Portable regressions cover the former lock cycle, concurrent startup, failed
recovery, configuration replacement, agent/route identity, active project
writers and UI races. Release acceptance also checks packaged saved-chat and
diagnosis behavior, concurrent work, saved answers, attachments and restart.

The lock cycle predates the T3 input adaptations: shared startup authority was
introduced in 0.2.0 and automatic queue recovery later acquired the scheduler
lock. Recent saved-work and concurrency changes exercised that unsafe order.
An empty test project did not reproduce the saved-work startup condition.
